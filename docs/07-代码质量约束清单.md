# Developer Portfolio Lab — 代码质量约束清单

> **版本**：v1.0  
> **生效日期**：2026-09-22  
> **性质**：硬性约束，不是建议。每次 Code Review 逐项对照检查。

---

## 核心原则

> **高内聚、低耦合、易扩展、易维护。**
>
> 写代码时默认问自己三个问题：
> 1. 这个模块改了，会不会影响别的模块？
> 2. 以后加新功能，是改现有代码还是加新文件？
> 3. 三个月后我回来读这段代码，能一眼看懂吗？

---

## 一、目录与依赖方向

### 1.1 依赖单向流动，禁止反向引用

```
views → features → services → supabase
  ↑        ↑
components/shared  composables
```

**禁止事项：**
- ❌ 一个 feature 直接 import 另一个 feature 的内部组件
- ❌ `components/ui/` 里出现业务逻辑
- ❌ `services/` 里出现 Vue 组件或 DOM 操作
- ❌ `utils/` 里出现 import 任何业务代码

### 1.2 Feature 内部自包含

每个 feature 是一个独立的黑盒：

```
features/projects/
├── components/     # 只有 projects 用的组件
├── composables/    # 只有 projects 用的逻辑
├── services/       # projects 相关 API 调用
├── types/          # projects 相关类型
└── views/          # projects 页面
```

**只有以下东西可以从 feature 导出给外部用：**
- `views/` 里的页面组件（被路由引用）
- 明确标注的公共类型（放 `types/`）

### 1.3 共享组件下沉规则

| 层级 | 放哪里 | 例子 |
|------|--------|------|
| 纯展示，无业务 | `components/ui/` | Button / Input / Dialog |
| 跨 2+ feature 复用的业务组件 | `components/shared/` | ProjectCard / EmptyState |
| 只在 1 个 feature 用 | 该 feature 的 `components/` | ProjectFilterBar |

**判断标准：** 先写在 feature 里，发现第二个地方要用再下沉。不要提前抽象。

## 二、组件设计

### 2.1 单一职责

- 一个组件只做一件事。如果超过 200 行模板，拆。
- 组件文件名 = 它做的事。`UserTable.vue` 对，`UserTableHelpers.vue` 错。
- Props 超过 5 个 → 考虑拆组件或用配置对象。

### 2.2 单向数据流

```
父组件 → props → 子组件
子组件 → emits → 父组件
```

**禁止：**
- ❌ 子组件直接修改 props
- ❌ 子组件直接 import 并修改父组件的状态
- ❌ 跨组件直接引用（兄弟组件不直接通信，通过父组件或 store）

### 2.3 组合优于配置

能用 slot 解决的，不要用 props 开关：

```vue
<!-- 好：灵活，可扩展 -->
<Card>
  <template #header>{{ title }}</template>
  <template #default>{{ content }}</template>
</Card>

<!-- 差：每个变体加一个 prop -->
<Card variant="header-with-avatar" showFooter />
```

### 2.4 Props 与 Emits 必须类型化

```typescript
// 必须这样
interface Props {
  items: Project[]
  loading?: boolean
  selectedId?: string
}
defineProps<Props>()

const emit = defineEmits<{
  (e: 'select', item: Project): void
}>()
```

**禁止：** `defineProps({...})` 用运行时声明方式（除非是非常简单的纯展示组件）。

## 三、状态管理

### 3.1 状态放哪里，边界清晰

| 状态类型 | 放哪里 | 例子 |
|---------|--------|------|
| 服务端数据（来自 API） | TanStack Query | 项目列表、文章详情 |
| 全局 UI 状态 | Pinia store | 暗色模式、命令面板开关 |
| 组件本地状态 | `ref` / `reactive` | 表单输入、展开收起 |
| 跨组件但非全局 | 父组件 props/emits | 列表选中项 |

**判断标准：** 这个数据删了对其他页面有影响吗？没影响 → 本地 ref。是从后端来的 → Query。

### 3.2 Store 设计原则

- 每个 Store 只管一个领域，不做大杂烩
- Store 里不写业务逻辑，只存状态和最小操作
- 复杂业务逻辑放 composable 或 service

## 四、Service 层与数据访问

### 4.1 组件不直接调 Supabase

```
组件 → useProjects() composable → project.service.ts → supabase
```

**好处：** 以后换后端，只改 service 层，组件一行不用动。

### 4.2 Service 函数签名规范

```typescript
// ✅ 好：输入输出都有明确类型
async function fetchProjectBySlug(slug: string): Promise<Project>

// ❌ 差：返回 any，调用方不知道拿到什么
async function fetchProjectBySlug(slug: string) {
  const { data } = await supabase.from('projects').eq('slug', slug).single()
  return data
}
```

## 五、可扩展性设计

### 5.1 配置驱动，不要硬编码

```typescript
// ✅ 好：加一个导航项只改数组
const navLinks = [
  { to: '/', label: 'Home' },
  { to: '/projects', label: 'Projects' },
  // 加新页面只加一行
]

// ❌ 差：每个地方都写一遍
<a href="/">Home</a>
<a href="/projects">Projects</a>
```

### 5.2 预留扩展点

布局组件、通用组件要预留 slot，以后加内容不用改组件本身：

```vue
<!-- 布局组件预留 slot -->
<AppLayout>
  <template #sidebar-extra>
    <!-- 以后这里可以加东西 -->
  </template>
</AppLayout>
```

### 5.3 类型先行

新功能先定义 Types / Zod Schema，再写实现。这样：
- 接口变更时 TypeScript 会告诉你哪里要改
- 前后端可以并行开发
- 自动有文档效果

## 六、易维护性

### 6.1 小文件原则

| 文件类型 | 行数上限 |
|---------|---------|
| Vue 组件 | ≤ 200 行模板 + 100 行逻辑 |
| Composable | ≤ 100 行 |
| Service 文件 | 按实体拆分，每文件一个领域 |
| Utils | 纯函数，单一职责 |

超了就拆。拆不动就说明设计有问题。

### 6.2 命名语义化

```typescript
// ✅ 好
const isProjectPublished = computed(() => project.status === 'published')

// ❌ 差
const isValid = computed(() => project.status === 'published')
```

### 6.3 注释策略

- 复杂业务逻辑必须写注释（为什么这么做，不是做了什么）
- 公共 API 必须 JSDoc
- 显而易见的代码不加注释
- 禁止注释掉的死代码（直接删，Git 里有）

### 6.4 魔法值禁止

```typescript
// ✅ 好
const MAX_PROJECTS_PER_PAGE = 12

// ❌ 差
if (pageSize > 12) { ... }
```

所有常量放 `utils/constants.ts` 或 feature 内部的 `constants.ts`。

## 七、Code Review 检查清单

每次 AI 生成代码后，人必须逐项检查：

### 架构层
- [ ] 依赖方向正确？（没有反向引用）
- [ ] 该 feature 内聚了吗？（没有跨 feature 乱引用）
- [ ] 共享组件放对层级了吗？

### 类型层
- [ ] 所有 Props / Emits 有类型？
- [ ] 没有 `any` 滥用？
- [ ] Service 函数输入输出类型完整？

### 状态层
- [ ] 服务端数据走 TanStack Query 了吗？
- [ ] 全局 UI 状态放 Pinia 了吗？
- [ ] 没有把服务端数据存 Pinia？

### 体验层
- [ ] Loading / Error / Empty 三态都有？
- [ ] 响应式布局覆盖了？
- [ ] 键盘可达？

### 维护层
- [ ] 文件大小在限制内？
- [ ] 命名语义化？
- [ ] 没有魔法值？
- [ ] 没有死代码？

---

## 八、违反后的处理

- 发现违反以上规范的代码 → 立即修改，不接受"先这样以后再改"
- 如果觉得规范不合理 → 讨论后更新本文档，而不是悄悄绕过
- 每次 Phase 结束时回顾：哪些地方代码味道重，下阶段改进
