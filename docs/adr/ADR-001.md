# ADR-001: Feature-based 目录结构与轻量分层（Pragmatic Clean）

**状态：** Accepted  
**日期：** 2026-09-22  
**关联文档：** [03-技术架构设计.md](../03-技术架构设计.md)

## 背景

需要为展示型平台确定代码组织方式。候选方案：
1. 完整 Clean Architecture（entities / use-cases / repositories / interfaces 分层）
2. MVVM / MVI 等移动端模式
3. 传统 `views/components/services` 三层
4. Feature-based 目录 + 轻量分层

约束：代码必须易扩展、易维护、高内聚低耦合（用户明确要求）；项目规模中等（公开站点 + Admin 后台）；需持续演进展示给招聘者。

## 决策

采用 **Feature-based 目录 + 轻量分层（Pragmatic Clean）**：

- 按业务域组织代码：`src/features/<domain>/{views,components}/`
- 跨域共享下沉到 `src/components/shared/`、`src/composables/`、`src/services/`
- 依赖方向单向：`features → services → app`（数据层在最底层）
- 不引入 use-case 抽象层：服务层方法（`getProjects` 等）即应用用例，通过 TanStack Query 消费
- 每个 feature 内部保持独立，删除/替换一个 feature 不影响其他 feature

## 后果

**正面**
- 新增页面 = 新增 feature 目录，不改动其他目录
- 依赖方向清晰，类型推断自然
- 比完整 Clean Architecture 少 2-3 层抽象，对中小项目更务实

**负面 / 权衡**
- 跨 feature 共享逻辑需要主动下沉（靠 code review 纪律）
- 完整 Clean Architecture 的"领域模型独立性"在此规模不必要（数据模型即领域模型）

**不使用 MVVM/MVI 的原因**：Vue Composition API 已提供 setup 级组合能力；额外引入 ViewModel/MVI 状态机层会增加样板代码，对展示型平台无收益。
