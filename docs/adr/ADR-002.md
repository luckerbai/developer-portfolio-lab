# ADR-002: TanStack Vue Query 作为服务端状态层

**状态：** Accepted  
**日期：** 2026-09-22  
**关联文档：** [03-技术架构设计.md](../03-技术架构设计.md)

## 背景

平台需要从 Supabase 异步读取项目、简历、设置等数据，并支持：加载态、错误态、缓存、失效重取、乐观更新（Admin CRUD）。

候选方案：
1. 每个组件自己 `onMounted` + `fetch` 管理状态
2. Pinia store 统一管理服务端数据
3. TanStack Vue Query（服务端状态与客户端状态分离）

## 决策

采用 **TanStack Vue Query 5**：

- 服务端状态（查询/变更）全部走 Query/Mutation，组件内 `useQuery`/`useMutation`
- Pinia 只保留**纯客户端状态**（主题偏好等）
- 查询键约定：`['projects-public']`、`['featured-projects']` 等，按领域命名
- Mutation 成功后 `invalidateQueries` 失效对应列表

## 后果

**正面**
- 加载/错误/缓存/去重/失效逻辑内置，组件代码显著变薄
- 与组件生命周期解耦（切页不丢缓存，回访零闪烁）
- 乐观更新提升 Admin 后台交互质感

**负面 / 权衡**
- 增加约 35KB gzip 依赖（已通过 vendor 分包缓解）
- 团队需理解 query key 失效模型（本项目已通过 Service 层单测固化行为）

**不选方案 2 的原因**：Pinia 管理服务端数据会导致缓存、请求去重、失效策略都要手写，且与服务端状态语义纠缠。
