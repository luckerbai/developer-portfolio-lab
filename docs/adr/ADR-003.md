# ADR-003: Supabase 作为后端平台

**状态：** Accepted  
**日期：** 2026-09-22  
**关联文档：** [04-数据库设计.md](../04-数据库设计.md)

## 背景

平台需要：Postgres 数据存储、用户认证（Admin）、行级安全（RLS）、存储（图片）、即时 API。候选：
1. 自建 Node.js API（Express/Fastify）+ Postgres
2. Firebase
3. Supabase（托管 Postgres + Auth + RLS + Storage）

约束：单人维护、展示型平台、希望把精力集中在**前端工程能力**本身，而非运维后端。

## 决策

采用 **Supabase**：

- 7 张表（`profiles/projects/experiences/skills/articles/site_settings/experiments`）+ RLS
- **公开读**策略：匿名用户只读 `published` 数据；Admin 通过 Supabase Auth 登录后写
- 数据库迁移文件 `supabase/migrations/001_initial_schema.sql` 进 Git，可复现
- 客户端用官方 SDK `@supabase/supabase-js`（Publishable Key 只含公开能力）

## 后果

**正面**
- 零后端代码：Auth / REST API / RLS / Storage 全部托管
- RLS 在数据库层兜底，前端即使暴露 key 也无法越权
- 迁移即代码，CI 可验证 schema

**负面 / 权衡**
- SDK 体积较大（gzip ~55KB，已通过 vendor 分包独立缓存）
- 复杂后端逻辑（定时任务等）不适合 SQL/RLS 表达——本项目无此需求
- 强依赖第三方平台（对展示型项目可接受）

**不选自建 API 的原因**：会增加一套 Node 服务、部署、鉴权、数据库迁移维护成本，与本项目"展示前端工程"的目标相悖。
